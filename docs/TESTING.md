## 1. The pyramid

```
        e2e flows (handful, critical)
              ▲
      integration / IT (API + Postgres)   ← bulk of coverage
              ▲
        unit (service logic)              ← fast, happy path + edge math
```

**Unit (JUnit, no Spring context):** service-layer logic where pure
Java/math/rule reasoning lives:
- `PhoneUtilsTest` — Indian mobile regex edge cases.
- `LeadScoringServiceTest` — rule-based heat scoring (HOT/WARM/COLD,
  boundaries at +30/+31/+90/+91 days, budget thresholds, LOST override).
- `DiscountPolicyTest` — discount-approval threshold (at/under/over limit,
  configurable percent, 0% revert).
- `PaymentReminderPolicyTest` — 3-day reminder horizon and day-label math.
- `FollowUpAutomationTest` — follow-up cadence (+5 min call, +1/+3/+8/+15-day
  ladder per spec §19.2, +2-day quotation, re-entry cancellation, booking closes ladder).
- `LeadServiceTest` — consent gate, lost-reason enforcement, LOST→COLD,
  invalid transitions, ownership.

**Integration (Spring Boot + real Postgres):** repository + API layers. In
this project the integration slices run against a real `postgres:16` via
`backend/src/test/resources/application-test.yml` pointing at
`securetravels_test`; `BaseIT` truncates the full table list (including
`webhook_logs`, `assignment_state`) between tests and Flyway rebuilds the
schema. CI provisions the database as a `postgres:16` service
(`.github/workflows/ci.yml`). Testcontainers is the *future* upgrade path
(throwaway DBs per run) — planned with the Phase 2 infra work, not a current
dependency.

## 2. Critical e2e flows that must always have a test

These are the pipeline-critical journeys. A change that touches any of them
MUST not delete or neuter their test:

1. **Lead creation → webhook → round-robin owner → 5-min task → notification.**
2. **Lead status stepper** `NEW → INTERESTED → QUOTATION_SENT →
   BOOKING_CONFIRMED` (and the LOST rules: reason required).
3. **Booking → ops handoff → travel arrangements → trip sheet** (auto-creates
   on CONFIRMED, no duplicates — invariant I6).
4. **Booking → payments** (advance + balance → COMPLETED, overdue sweep).
5. **Auth session lifecycle** (login → refresh rotation → reuse rejected →
   logout → token invalid).
6. **Ownership isolation** (SALES A cannot see/mutate SALES B's lead; 403).
7. **Duplicate handling** (UI 409 vs webhook 200 duplicate:true) and consent
   enforcement (DPDPA).
8. **Discount approval threshold** — at-or-below-limit auto-approved by sales;
   over-limit blocked for sales and manager-unblockable (`DiscountPolicy`).
9. **Seat-hold concurrency** — two parallel claims on a one-seat batch admit
   exactly one booking; seats never go negative (`Phase1HardeningIT`).

## 3. Frontend

- `npm run lint`, `npm run typecheck`, `npm run build` mirror CI exactly.
- Typed client coupling: after any backend change run `npm run openapi:gen`;
  a schema change that breaks payloads will fail `tsc` — that is the safety
  net for API parity.
- No component-test framework yet; the typed client + build gate are the
  phase-1 safety net (component/UI tests are a Phase-3 candidate alongside
  the ops mobile app).

## 5. Rules of the road

1. A bug fix ships with a **regression test** that fails on the old code.
2. New endpoints ship with an IT covering success + the failure envelope
   (see `API_STANDARDS.md` error table).
3. Tests run against `securetravels_test`, never the dev DB.
4. Sweeps/time logic is tested by clock-driven due dates, not `sleep()`.
5. Keep the suite deterministic: no reliance on row order — sort or assert on
   unique keys (`WebhookAutomationIT` sorts `findAll()` by
   `createdAt.thenComparing(id)` for round-robin assertions).
